## 🔴 严重：会导致错误结果或数据损坏

### P-01 HOTP 账号被静默当作 TOTP 处理

- **位置**: `models.py:33` · `_cli.py:205-215` · `_cli.py:257`
- **问题**: `parse_otp_uri` 能解析 `otpauth://hotp/...`，但 `Account` 模型没有 `otp_type` 字段，`add_account` 也不接收该参数。HOTP 是基于计数器的，而 `generate_totp` 基于时间——HOTP 账号保存后展示的时间码永远不会被服务端接受，且无任何警告。
- **影响**: 用户扫描 HOTP 二维码，看到"添加成功"，但验证码永远是错的，无从排查。
- **修复建议**: 添加时检测 `otp_type == 'hotp'` 明确拒绝并提示"暂不支持 HOTP"，或实现计数器机制。
- **修复方案（最终版）**: 采用方案 A（明确拒绝非 TOTP）。**类型判断唯一收敛在 `parse_otp_uri` 一处**：`otp_type != 'totp'` 时 `raise UnsupportedOTPTypeError(otp_type)`，并显式 `except UnsupportedOTPTypeError: raise` 穿透外层。两个 scan 函数不再做手工类型判断，只保留"解码来源"差异，共用 `_extract_otp_info` 提取逻辑。CLI 捕获后一行文案："✗ 该二维码是 HOTP 协议，本工具仅支持 TOTP。"（不解释原理，任何非 totp 类型统一该格式）。
- **状态**: ✅ 已修复

### P-02 备份文件不可跨安装移植，错误提示误导

- **位置**: `crypto.py` · `storage.py:227` · `_cli.py:484-485`
- **问题**: 导出的 `secret_encrypted` 用本机随机 master key 加密。在另一台电脑全新安装后导入，即使主密码完全相同，`decrypt()` 也抛 `InvalidTag`。而错误提示是"主密码不匹配或文件已损坏"——实际与主密码无关，是主密钥不同。
- **影响**: 用户反复重输主密码仍失败，误以为密码记错，可能清空数据重建。备份/迁移功能实际不可用。
- **修复建议**: 提示改为"备份来自其他安装，需先迁移主密钥文件（master.key）"，或提供导出主密钥的选项。
- **修复方案（已实施）**: 采用"备份内嵌主密钥 + 导入按本机状态分流"。
  - **导出**: `export_json` 内嵌 `master_key` 字段（本机 master.key 完整内容，仍由主密码加密）。
  - **导入分流**:
    - 备份含 `master_key` → 先验证备份密码（`load_external_key`），失败即终止且本机状态不变。
    - **情况 A**（本机空库）：`adopt_external_key` 替换本机主密钥，数据原样入库，之后用备份密码登录。
    - **情况 B**（本机已有账号）：`import_json(external_key=...)` 用备份密钥解密→本机密钥重加密合入，本机密码/主密钥不变。
  - 旧版备份（无 `master_key`）走原逻辑，兼容。
  - 新增 crypto 方法：`get_key_data`、`load_external_key`、`decrypt_with_key`、`adopt_external_key`。
- **对抗性审查补充（P-02/P-03 修复后发现 5 个新问题，已修复）**:
  1. `decrypt`（同机路径）未统一转 ValueError → 导入含错误密钥密文时 `InvalidTag` 崩溃整个导入。已修复：`decrypt` 与 `decrypt_with_key` 对称，损坏统一抛 `ValueError`。
  2. `load_external_key` 对字段缺失/数据损坏给出"密码错误"误导。已修复：损坏抛 `ValueError`，密码错返回 `None`，CLI 分开提示。
  3. P-01 多二维码：图片同时含 HOTP+TOTP 时遇到 HOTP 即抛，不继续找 TOTP。已修复：`_extract_otp_info` 遇到非 totp 先记录、继续找，全非 totp 才抛。
  4. `import_json` 的 `skipped` 混淆"冲突跳过"与"损坏跳过"。已拆分 `conflict_skipped` / `damaged_skipped`，CLI 分别显示。
  5. 情况 A 的 `adopt_external_key` 时序在导入之前，导入失败时本机 key 已被替换。已改为导入成功后执行。
- **状态**: ✅ 已修复（153 测试通过 + 端到端验证）
- **第二轮对抗性审查补充（已修复）**:
  1. 🔴 **情况 A 时序 bug（严重）**: CLI 情况 A 先 `import_json`（未传 external_key，本机新 key 解不开备份）再 `adopt_external_key` → 实际导入 0 账号。已改为**先 adopt 换 key 再 import**（preview_import 前置校验格式，拦截了会导致 key 被替换的损坏场景）。真实 CLI 调用验证通过。
  2. 🟠 **preview 与实际导入不一致**: 损坏条目 preview 归 to_import，CLI 显示"将导入 X"但实际 damaged_skipped。已为 `preview_import` 增加 `external_key` 参数做解密校验，损坏条目归 `damaged`，CLI 单独显示"损坏无法导入 N 个"。
  3. 其余路径（情况 A/B/C、P-03 冲突、decrypt/_load_key/load_external_key 异常对称）全部验证通过，无新问题。
- **状态**: ✅ 已修复（155 测试通过 + 真实 CLI 集成验证）

### P-03 导入不更新已存在账号，密钥轮换后恢复丢失新密钥

- **位置**: `storage.py:239-240`（`except ValueError: pass`）
- **问题**: `import_json` 遇到同 `(issuer, account)` 账号直接跳过。用户重置 2FA 密钥后导出→导入，旧账号被保留、新密钥被丢弃，恢复的是过期旧密钥。
- **影响**: 数据静默不一致，用户以为恢复最新备份，实际是旧密钥，登录时全部失效。
- **修复建议**: 导入时对已存在账号明确提示"将覆盖旧密钥"并让用户选择。
- **修复方案（已实施）**: 导入冲突逐账号决策，**当前/备份不混用**（选一个则整体用那个版本）。
  - storage: 新增 `find_by_identity`、`overwrite_account`（整体覆盖含密钥）；`import_json` 增加 `decisions` 参数，返回 `{'imported','updated','skipped'}`。
  - CLI: 预览后对每个已存在账号询问"用当前的还是备份的？[当前/备份，默认当前]"，默认保留当前（安全）。
  - 逻辑: 决策 `'backup'` → 用备份密钥解密→本机 key 重加密→整体覆盖；`'current'` 或无决策 → 跳过。
- **状态**: ✅ 已修复（146 测试通过 + 密钥轮换端到端验证）

### P-05 首次设置主密码失败即退出，不可重试

- **位置**: `_cli.py:510-518`
- **问题**: 密码强度不达标或两次不一致 → `sys.exit(1)`。用户必须重启整个程序、重看 banner、重新输入。
- **影响**: 常见输入错误（大小写、多打一位）就全盘重来，体验差。
- **修复建议**: 用循环重试，而不是直接退出。
- **修复方案（已实施）**: 首次设置主密码改为循环重试。
  - **先告知规则**：输入前显示"密码要求：至少 6 位，且包含大写字母、小写字母和数字"。
  - **循环重试**：密码不达标 / 两次确认不一致 → 提示具体原因 + "剩余 N 次尝试"，回到重新输入，不再退出。
  - **5 次上限**（`MAX_PASSWORD_ATTEMPTS`）："密码+确认"整个环节共用 5 次，5 次仍失败 → "✗ 主密码设置失败：已尝试 5 次。请重新运行 mini2fa 重新设置。" → 退出，且不生成 key 文件。
  - 新增常量 `PASSWORD_REQUIREMENTS` / `MAX_PASSWORD_ATTEMPTS`。
- **状态**: ✅ 已修复（158 测试通过 + 3 场景端到端验证）

### P-06 无法清空分类/备注

- **位置**: `_cli.py:308-318`
- **问题**: 编辑时回车=保持不变，空字符串不触发更新（`if category and ...`）。用户一旦填过备注，就永远无法删除它。
- **影响**: 分类无法清回默认值，备注无法删除。
- **修复建议**: 提供类似"输入 `.` 表示清空"的机制。
- **修复方案（已实施）**: 引入清空哨兵 `.`。编辑分类/备注时三种语义：回车=保持不变；输入 `.`=清空（分类回 `default`，备注置空）；其它文字=更新为新值。提示文案改为"输入新值（直接回车保持不变，输入 . 清空）"。`.` 仅在字段本来有值时生效，避免误导。新增 3 个测试覆盖三种语义。
- **状态**: ✅ 已修复（161 测试通过）

### P-07 无修改主密码功能

- **位置**: 全局
- **问题**: 主密码一经设置不可修改。忘记密码只能删除 `master.key` 重建（丢失全部数据）。
- **影响**: 无改密入口，密码泄露后无法自救。
- **修复建议**: 添加"修改主密码"菜单项（验证旧密码 → 输入新密码 → 用新密码重新加密 master key）。
- **修复方案（已实施）**: 新增菜单项"7. 🔒 修改主密码"。
  - `crypto.py` 新增 `change_password(old, new, hint)`：验证旧密码 → 用新密码派生新 KEK 重新加密 master_key → 写回文件。**master_key 不变，数据库 secret 全不用动**；新 salt+nonce 使旧密码立即失效。
  - `_cli.py` 新增 `handle_change_password`：旧密码验证（3 次）→ 新密码强度校验（5 次）→ 确认 → 重设提示（回车保留原值）。
  - 新增 5 个测试：改密成功/旧密码失效/新密码生效/hint 保留、错误旧密码拒绝、数据仍可解密、CLI 流程。
- **对抗性审查发现并修复（严重）**: `change_password` 用 `_load_key` 验证旧密码，失败时 `_load_key` 的副作用会**清空 self.key**——会话内改密失败后，后续所有加密操作崩溃（"未初始化密钥"）。CLI 的 `handle_change_password` 用 `initialize` 验证旧密码也有同样问题（3 次失败后会话崩溃）。
  - 修复：新增 `verify_password`（验证失败恢复原 key，不污染会话）；`change_password` 和 `handle_change_password` 改用 `verify_password`。
  - 新增 2 个 `TestVerifyPassword` 测试。
- **状态**: ✅ 已修复（168 测试通过）

### P-09 添加账号流程顺序不合理

- **位置**: `_cli.py:196-218`

  - **先填字段**：分类/备注移到确认之前。
  - **完整摘要确认**：确认时展示"服务商/账号/分类/备注"完整摘要，用户一次确认，确认内容即入库内容。
  - 新增 3 个测试（查重拦截/新账号入库/取消不入库）。
- **状态**: ✅ 已修复（175 测试通过）

### P-15 SQLite 损坏/锁定无保护

- **位置**: `storage.py:126-139`
- **问题**: 数据库文件损坏或并发锁定时，`get_all_accounts` 直接 traceback 崩溃。
- **影响**: 2FA 数据库是用户的命根子，读取路径应优雅报错。

- **状态**: ✅ 已修复
